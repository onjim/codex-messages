# Codex 折叠渲染 (codex-messages)

把模型回答按 `phase` 归组：中间旁白、思考与工具调用收进一个可展开分组，只留最终答案平铺，对齐 Codex 客户端的折叠呈现。

---

## 它凭什么判断折叠

一个 Responses turn 的输出项按到达顺序是平铺的独立条目：`reasoning` → `message` → `function_call`。本插件不按「某个块是否可折叠」处理，而是**按 `phase` 把同一轮的输出归组**，再把非最终答案的部分收进一个分组：

- `reasoning`（摘要）：暂存为待折叠内容。
- `function_call` / `function_call_arguments`：暂存为命令执行块，同样待折叠。
- 带 `phase` 的 `message`：决定性锚点。
  - `commentary`：这一条是中间旁白。它前面那段 reasoning 加同轮的 function_call 归到同一个分组下，**标题就用这条 message 的文本**——折叠后看到的是「我准备做 X」，展开才是推理和命令。
  - `final_answer`：本轮真正的回复，普通气泡平铺，不折叠。
- `reasoning` 本身在规范里没有 `phase`，它是靠「归属于哪条 `commentary` message」被间接吸收的。

`phase` 是给客户端的**分组标签**，不是渲染开关。渲染规则（按 phase 切分、吸收前导 reasoning/call）在客户端，服务端只负责把每条 message 标成正确的 phase。

## 宿主没有 phase 时怎么办

pi-web-ui 的消息对象上没有 `phase` 字段（实测 `~/.pi/agent/sessions/*.jsonl`：assistant 消息只有 `content` 里的 `thinking` / `text` / `toolCall` 三种块）。所以插件先问服务端要 phase，拿不到就按结构推断，二者语义一致：

| 信号 | 判定 |
| --- | --- |
| 服务端消息带 `phase: "commentary"` / `"final_answer"` | 直接采用（权威） |
| 该条还带工具调用 | `commentary`（本轮还没干完） |
| 只剩正文、无工具调用 | `final_answer` |
| 只有思考、没有可见正文 | `commentary` |
| 用户消息 / 系统消息 / 压缩摘要卡 | 边界，打断归组 |

宿主自己已经把中间步骤聚成 `.turn-tools-trail`，整条 trail 直接当一个分组成员，不需要重新拼。

## 折叠头只显示状态

折叠头不放标题、不放标签，只两种状态：

- **生成中**：`工作中`（绿色呼吸），分组保持展开，能实时看到工具卡在跑。
- **完成后**：`工作 8.2 秒` / `工作 31 秒` / `工作 1 小时 5 分`，按折叠样式收起来。

耗时按三级兜底算：服务端每条消息的 `durationMs` 累加 → 组内所有消息（含 trail 里嵌套的）与最终答案的毫秒时间戳做首尾差、再补最后一条的生成时长 → 本地观测到「工作中」起的计时。消息 id 与宿主 cluster id 都形如 `a-1793608921818-81`，中间那段就是毫秒时间戳，所以历史会话也能还原真实耗时。三者都拿不到才显示 `已完成`。

## 最终答案自带的思考也一起收

模型经常把本轮最后一段 reasoning 挂在**最终答案那条消息**上（宿主就把它渲染在答案正文上方）。如果只收中间步骤，答案上面会孤零零露出一段思考，读起来像被切成了两段。

插件因此做「向下附着吸收」：分组成型后，往下找紧随其后的那条 `final_answer` 消息（中途遇到用户消息或另一个分组即停，说明已换轮），把它的思考块标成该分组的一部分（`data-cm-attached=<groupKey>`），折叠时跟分组一起隐掉，展开时随分组一起回来。答案正文始终留着。

这也符合原始模型：`reasoning` 在规范里没有 `phase`，它是靠归属于哪条 `commentary` 被间接吸收的——本轮的 reasoning 属于这一轮，不属于答案。

## 流式期间的行为

这是关键的一点，实测校准过：

1. **本轮还在跑**且分组是最后一个 → 分组**保持展开**，用户能实时看到 agent 在干活（而不是屏幕空着）。
2. 最终答案落地后，分组不再是尾段 → **自动折叠**，步骤数标头更新为完整值。

「还在跑」用两个信号取或：服务端 `isStreaming`，以及宿主自己在运行期渲染的 `.btn.stop`。必须把关，否则历史会话里恰好排在末尾的分组会永远展开。

## 实现约束（为什么是 DOM 层归组）

宿主没有消息渲染钩子：`messageWidgets` 只作用于 `role: "custom"` 的消息，`renderers` 只作用于代码块。所以本插件在 DOM 层做归组，并守住三条不跟 React 抢地盘：

1. **绝不搬动宿主节点**。只 `insertBefore` 自己的分组头，收起靠成员上的内联 `display: none`，展开靠移除该属性。
2. **标记全用自有属性**（`data-cm-group-head` / `data-cm-member` / `data-cm-key`）。React 只会改写 class，不会碰这些，所以标记不会被悄悄改掉。
3. **签名 + 完整性双检**。布局签名（会话、phase 版本、是否在跑、分组结构、折叠选择）没变就一次 DOM 都不碰；但签名相同不代表痕迹还在——分组头可能插在宿主自有的 trail 内部，被 React 重渲染时丢掉，因此还要核对头/成员数量与键是否对得上，对不上立即重建。已实测：手动删掉注入的头，下一帧自动恢复。

归组以 `.messages` 的**直接子节点**为单位。宿主为了窗口化渲染，会把真消息包在无 class 的懒挂载壳里（`data-lazy-id`），更早的历史是 `.msg-lazy-ph` 占位；解包后判定，收起时隐整个外壳，因此不会打乱宿主的可见性计算（已实测反复滚到顶部加载更早消息，节点数与折叠状态稳定）。

## 配置

无配置项，行为固定：整轮（turn）中间步骤合成一个分组，收尾后默认折叠；手动展开/收起的选择按会话记忆。想停用直接在「设置 → 插件」里禁用本插件即可，禁用后完全恢复宿主原本的平铺呈现，不留任何痕迹。

## HTTP 接口

- `GET /plugins-api/codex-messages/turns?session=<id>`：逐条 phase 与元信息，含 `explicit`（是否有服务端显式 phase）与 `streaming`。

## 已实测

在 pi-web-ui 0.113.1 + 真实会话上验证过：

- 历史会话载入即折叠，折叠头显示「工作 8.2 秒」这类真实耗时。
- 手动展开/收起后刷新，选择被记住（按会话 + 稳定分组键存 `localStorage`）。
- 分组键对增长稳定：流式期间步骤从 1 涨到 3，键不变，手动选择不失效。
- 实时一轮：跑动中分组展开可见工具卡，答案落地后自动折叠。
- 禁用插件后，注入的头、成员标记、附着思考块、内联样式、trail 的 `display` 全部还原，无残留属性。
- 滚动加载更早消息不串位；无新增控制台报错。

## 已知边界

- 只吸收紧邻分组的**第一条**最终答案的思考；若同一轮后面还有别的答案消息，它们的思考保持宿主原样。
- 归组发生在渲染之后，所以极长会话首次折叠有一帧内的高度变化；签名缓存使它只在结构变化时发生。
- 宿主若改了消息 DOM 的 class 命名，识别点集中在 `resolveUnit` / `classifyUnit` / `hasToolCard` 三处，按新命名调整即可。
